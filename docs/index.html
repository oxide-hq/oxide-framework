Oxide Docs

Prologue

Meet Oxide

Building a web application should feel like describing your domain, not wiring plumbing. Oxide gives you the parts of Laravel that make you fast (expressive routes, form requests, route-model binding, an Eloquent-style ORM and fluent HTTP tests) and lets the Rust compiler check every one of them before your code ever runs.

Oxide is a set of crates on top of Axum 0.8 and Tokio. Nothing is resolved by reflection at runtime: the container, validation, bindings and query methods are generated at compile time, so a typo in a route name or a missing field is a build error rather than a 500 in production.

Routing

Declare routes, prefixes, middleware groups and resources with the routes! DSL.

 Form Requests

Parse, authorize and validate input before your handler runs.

 Eloquent Models

#[derive(Model)] generates typed queries and active-record methods.

 HTTP Tests

Send requests and chain assertions without starting a server.

Why Oxide?

Rust gives you speed and correctness, but most of its web stacks ask you to assemble the developer experience yourself. Oxide takes the conventions that make Laravel teams productive and expresses each of them as a zero-cost Rust abstraction.

Here is a complete endpoint that loads a post from the URL, checks the incoming form, saves the change and returns JSON. If the post does not exist you get a 404, if the input is invalid you get a Laravel-shaped 422, and you wrote none of that by hand.

Design principles

A framework is a set of decisions you no longer have to make. These are the ones Oxide makes for you, and the reasons behind them.

  • Compile time over runtime. Derives and macros generate the code a container or ORM would otherwise resolve at runtime, so mistakes surface in cargo check.
  • Laravel's names, Rust's types. If you know FormRequest, route() or where(), you already know where to look.
  • Plain Axum underneath. Every Oxide router converts into an axum::Router, and every Tower layer and Axum extractor still works.
  • Safe by default. Every SQL value is a bound parameter, validation errors never leak internals, and database failures render as an opaque 500.

The crates

Oxide is split into layers so each stays small and focused, but your application only ever depends on one of them: the oxide umbrella crate, which re-exports the rest.

Prologue

Installation

The quickest way to learn a framework is to run something real. In a few minutes the oxide installer will scaffold an application with a model, a controller, validation and passing feature tests.

Requirements

Oxide targets current stable Rust and promises to keep building on older compilers back to its minimum supported version. That gives you modern language features without forcing an upgrade the moment a new toolchain ships.

  • Rust 1.88 or newer (edition 2024).
  • A database: SQLite is bundled with sqlx, so there is nothing to install. PostgreSQL works too.

Installing the Oxide installer

Oxide is not on crates.io yet, so install the CLI straight from GitHub. It puts an oxide binary in ~/.cargo/bin.

Creating an application

Run oxide new and answer a few questions, much like laravel new. The installer asks for a name, a preset, a database, a starter and whether to install the AI agent skill.

Any answer you pass as a flag skips its question, and -n skips them all and uses the defaults: the api preset, SQLite, the blog starter and the agent skill. That suits scripts and CI.

PresetWhat you get
apiA JSON API: models, migrations, controllers, form requests and feature tests. The blog starter adds a working Post resource; blank starts with a health check.
minimalRouting and the service container only, with no database.

A fullstack preset with server-rendered views is planned. It will arrive with Oxide's templating layer.

A PostgreSQL application reads its connection from DATABASE_URL, both when it runs and in its tests. Each test gets its own schema, so they can run in parallel against one server. Copy .env.example to .env and set the URL before you run cargo test.

Read Directory Structure next for a tour of the files, and Artisan Console for the generators.

Adding Oxide to an existing project

You can also add Oxide by hand. Depend on the oxide crate from GitHub, plus the crates whose derives appear in your own code, such as serde, validator and sqlx.

Oxide uses sqlx 0.8 rather than 0.9, because 0.9 needs Rust 1.94, which is above Oxide's minimum supported version. Pin the same major in your project so you don't compile two copies of sqlx.

An Oxide application is an Axum application with better ergonomics. You describe your state, declare your routes, then hand the result to axum::serve. Oxide re-exports Axum as oxide::axum.

Working on Oxide itself

If you are contributing to the framework, the repository ships a justfile with the same checks CI runs. Running it before you push saves you a round trip.

Configuration

Every setting lives in one typed struct per file under config/. Environment variables and .env files override the file, and the whole lot is validated once at boot, so a typo fails at start-up with every problem listed instead of at first use.

Defining a section

Derive Config on a struct that also derives Deserialize. file names the TOML file, and each field can name an environment variable and a default.

A value comes from, highest first: its environment variable, the TOML file, then its default. Environment strings are converted to the field's type ("yes" for a bool, "a,b" for a Vec<String>, an empty string for an Option). Implement EnvValue, or use impl_env_value_as_string!, for your own enums.

Loading and using it

Put the returned Configuration in your service container. Handlers then take any section as an extractor, and code inside facade_middleware can use config_of, like Laravel's config('app'):

Environments and .env files

APP_ENV selects the environment: local (the default), testing, staging, production, or a name of your own. config.environment() returns it, with helpers such as is_production().

Oxide reads .env next to Cargo.toml. When .env.<APP_ENV> exists (say .env.testing), it replaces .env entirely, as in Laravel. The real process environment always wins over both files. Oxide never writes to the process environment, so tests can't disturb each other.

Boot-time validation

Every section is loaded and checked before the server starts, and every problem is reported at once with where it came from:

Add validate to the section (#[config(file = "mail", validate)]) and also derive validator::Validate to check ranges and formats, reported the same way.

Secrets

Mark a field #[config(secret)] and Debug prints [REDACTED] instead of its value, as do error messages. Config writes the Debug impl for you, so don't derive Debug on a section. Keep real secrets in the environment or an untracked .env, never in a committed TOML file.

Testing

Build a configuration without touching the environment: .vars([("APP_PORT", "8080")]) replaces the process environment and .env files, .root(dir) points at a directory holding config/, and .provide(AppConfig { .. }) inserts a ready-made section.

Prologue

Request Lifecycle

Knowing what happens between cargo run and a response makes the rest of the framework easier to reason about. Oxide's lifecycle has a start-up phase that runs once and a request phase that runs for every request.

Start-up

Application::builder()….build().await assembles the application in four steps:

  1. Register. Every service provider's register runs, in the order you added them. Providers only bind services here, because other services may not exist yet. Providers that declare provides are deferred and skipped.
  2. Override. Bindings made with .bind(..) on the builder run next, so they replace a provider's defaults. This is how tests swap a contract's implementation.
  3. Check. Anything a provider declared with bindings.require::<T>() must now be bound. If not, the build fails with every missing service listed at once.
  4. Boot. The container is complete, and each provider's boot runs in order. A provider may resolve services, read configuration or check a connection here. A failure stops the build and names the provider.

Then the providers' routes and the builder's routes are merged, and a middleware that starts a request scope is layered on top.

Each request

  1. The scope middleware gives the request its own Scope.
  2. Your middleware runs, outermost first, and the router picks a handler.
  3. Extractors run: Inject<T> resolves services from the scope (scoped services are built once for this request), and Config<T>, Validated<T> and Bind<T> do their jobs. A failing extractor ends the request with its own error response.
  4. The handler runs, and its response flows back out through the middleware.

See Service Providers for the container itself and Configuration for what is loaded before any of this.

The Basics

Routing

Your routes are the table of contents of your application, so they should read like one. The routes! macro lets you declare every endpoint, prefix and middleware group in one readable block, and checks it at compile time.

Basic routes

Most routes map an HTTP verb and a path to a handler, and that is all you should have to write. Any Axum handler works, including ones that take Oxide extractors such as Validated or Bind.

The available verbs are get, post, put, patch, delete, head and options. Paths use Axum's {param} syntax, and wildcard segments such as {*path} work as well.

Named routes

Names let you generate URLs without hard-coding paths, so you can change a URL in one place. Add .name() after any route; a duplicate name anywhere in the block is a compile error.

Read URL Generation to see how names turn back into URLs.

Route prefixes

APIs are usually versioned, and repeating /api/v1 on every line is noise. A prefix block prepends its path to everything inside it, and blocks nest as deeply as you like.

Add .name("admin.") to a prefix to prepend that string to every route name inside it, just like Laravel's name() on a group. Prefixes are flattened at compile time, so the expansion never nests Axum routers.

Middleware groups

Some routes need extra protection or behaviour that the rest of your API does not. A middleware block applies any Tower layer to the routes inside it and nowhere else.

Routes in different blocks may share a path with different verbs. In the example, GET /posts and DELETE /posts/{post} both work even though only the delete route sits behind the middleware.

Resource routes

Most models need the same five endpoints, and writing them out by hand invites inconsistency. resource registers all five with conventional paths, names and a singular route parameter.

VerbPathActionName
GET/api/v1/postsindexposts.index
POST/api/v1/postsstoreposts.store
GET/api/v1/posts/{post}showposts.show
PUT / PATCH/api/v1/posts/{post}updateposts.update
DELETE/api/v1/posts/{post}destroyposts.destroy

Customizing resources

Not every resource needs every action, and some names don't singularize neatly. Pass only or except to pick actions, and param to choose the parameter name.

The parameter defaults to the singular of the last path segment: /posts becomes {post} and /categories becomes {category}.

Serving the router

Routes are only useful once they're attached to your application's state. Call with_state to provide it and into_axum to get an axum::Router you can serve or compose further.

An OxideRouter still lets you compose by hand: nest_prefix("/v2", child), merge(other), layer(..) and route_layer(..) all keep the route-name registry in sync.

The Basics

Middleware

Middleware wraps a request: it can inspect it, change it, stop it, or change the response on the way out. Oxide keeps Axum's model and adds Laravel's vocabulary on top of it: global middleware, named aliases with parameters, groups, priority and terminable middleware.

Writing middleware

Call next.run(request).await to continue and receive the response, or return a response to stop. For a short one, middleware_fn(|request, next, params| async move { .. }) turns a closure into middleware. Services come from the request's scope: request.extensions().get::<Scope>() then scope.resolve::<T>(). An OxideHttpError returned by middleware goes through the exception handler like any other.

Registering it

Everything after the colon is a parameter: role:admin,editor calls EnsureRole with ["admin", "editor"]. A group's members can be aliases with parameters or other groups. route_middleware_without(&["api"], &["throttle"]) is the api group minus throttle, Laravel's withoutMiddleware.

Group members are checked when the application is built, so a typo there fails at start-up. A route naming an unregistered alias answers a plain 500 and logs the reason.

Order and priority

Middleware runs in the order you list it, outermost first. When one must always run before the others, override priority(): a higher number runs earlier, equal priorities keep their listed order, and it applies to global stacks and to each route_middleware list alike.

Terminable middleware

Return true from terminable() and implement terminate(&Outcome) to run work after the response is produced, such as recording metrics. It runs on a spawned task with the method, path, status and headers of the finished request, so it never slows the response and cannot change it.

The Basics

Controllers

Controllers keep related request handling in one place, so a teammate can find every post endpoint by opening one file. In Oxide a controller is a plain struct whose associated functions are Axum handlers.

Resource controllers

A resource controller answers the five standard actions for a model. Because each action is an ordinary async function, you choose exactly which extractors it needs.

Keep resource controllers to five actions. index, store, show, update and destroy are the whole vocabulary. When you need another verb, such as publishing a post, give it its own single-action controller instead of growing the resource.

Single-action controllers

Some operations are verbs of their own, and they read best as their own type. A single-action controller has one handle function that you route to directly.

Handling failure first

Handlers are easiest to read when the success path is the last thing you see. Return early with let ... else or ? instead of nesting if blocks.

The Basics

URL Generation

Hard-coded paths break the moment you rename a route. Generating URLs from route names means you change a path in exactly one place, and Oxide tells you when a name or parameter doesn't exist.

The route! macro

route! is Oxide's answer to Laravel's route() helper. Pass a route name and its parameters, and you get the path back as a String.

Parameters can be any value that implements Display. Values are percent-encoded, and parameters that aren't in the path become the query string.

route! panics if the name is unknown or a required parameter is missing, like Laravel's helper. Use url_for wherever a bad name could come from input.

Fallible URL generation

When you would rather handle a missing route than crash, call url_for. It returns a Result you can propagate with ?.

Inside handlers

A handler sometimes needs the URL of a resource it just created, for example in a Location header. The UrlGenerator extractor reads the same registry the router built.

The process-wide registry behind route! and url_for is filled when you call with_state or into_axum. Build your router before generating URLs, as your main and your tests already do.

The Basics

Service Container & Facades

Handlers should ask for what they need, not dig it out of a global. Oxide's container lets a handler take a mailer or a database pool as an ordinary argument, and the compiler proves it exists.

Defining services

A service is any cloneable type your handlers depend on. Deriving Service makes it an Axum extractor, so you can drop the State(..) wrapper from your signatures.

The application container

Your application state is the container: every field is a service. Deriving ServiceContainer generates a FromRef impl for each field, which is how Axum hands the right service to each handler.

Each type may appear only once in a container; a second Mailer field is a compile error, because the container could not tell them apart.

Facades

Deep inside a call stack, threading a service through every function can be more trouble than it's worth. Facades give you request-scoped static access, backed by a Tokio task-local rather than a global.

resolve panics with a helpful message outside a request scope; use AppContext::try_current() when you need to check first.

Never hold a std::sync::MutexGuard across an .await. Lock, read or write, and drop the guard before awaiting, or switch to tokio::sync::Mutex if the lock truly has to span an await point.

The Basics

Service Providers

Providers are where an application, or a package, wires itself in: they bind services, run start-up work and contribute routes. An Application assembles them in order and hands you something you can serve or test.

Two containers, one rule

#[derive(ServiceContainer)] stays the zero-cost way to share services you know when you write the state struct. The container here is for what is only known at boot: trait-object contracts, services registered by packages, and per-request services. Handlers can use both.

A provider

Declare a contract trait with Send + Sync supertraits (trait Mailer: Send + Sync) so dyn Mailer can live in the container.

Building the application

In a test, app.test_client() gives you a TestClient over the same application, and .bind(..) on the builder swaps an implementation:

Lifetimes

MethodBuiltUse for
singleton(value), singleton_arc::<T>(arc)once, nowPools, clients, configuration
lazy(|scope| ..)once, on first useExpensive services that may never be needed
scoped(|scope| ..)once per requestThe current user, a request-wide unit of work
transient(|scope| ..)every resolveCheap, stateful helpers

A later binding for the same type replaces an earlier one. Factories receive the Scope and can resolve their own dependencies. Singletons are built outside any request, so a singleton that asks for a scoped service gets an error instead of caching one request's data. A loop between services is reported as an error naming the path (A -> B -> A), and a scoped service asked for outside a request is an error too. Inside a request, Inject<T> is the extractor; elsewhere use container.resolve::<T>(). Resolution failures in a handler answer a plain 500 Server Error, and the details go to stderr.

Required and deferred services

A provider can declare what it needs with bindings.require::<dyn Mailer>(). If nobody binds it, build() fails and lists everything missing, instead of the first request failing. A provider that returns keys from provides() is deferred: it registers only when one of those services is first resolved, and its boot and routes never run. Use that for self-contained services that need no start-up work.

Packages

A package ships a provider, and its users add it with .provider(..). The provider binds the package's defaults (which the application can override with .bind(..)), reads its settings through app.config::<Section>() and contributes routes. Copying a package's config and migration stubs into the application arrives with the console commands.

The Basics

Form Requests & Validation

Validation belongs next to the data it describes, not scattered through your handlers. A form request is a struct that knows how to parse, authorize and validate itself, so by the time your handler runs the input is already trustworthy.

Creating form requests

You describe the payload once with serde and validator attributes. Deriving FormRequest connects it to Oxide's request pipeline.

Using form requests

Ask for Validated<T> in your handler and Oxide does the rest. If anything fails, your handler never runs.

Each request goes through four steps, in order:

StepOn failure
Parse the body as JSON (application/json, *+json) or a form (application/x-www-form-urlencoded)400 Bad Request
Run authorize403 Forbidden
Run the validation rules422 Unprocessable Entity
Hand the value to your handler

Authorizing requests

Whether a user may perform an action is part of the request, just like its shape. Add #[form_request(authorize)] and implement Authorize for your application state.

Because Authorize is implemented for a concrete state type, it can reach any service in your container, such as a policy or the database.

Authorize against an identity your authentication middleware has verified, such as a user it stored in the request extensions. Never trust a role or user ID sent in a header or the request body: any client can set those.

Validation error responses

Front-end code shouldn't need to know your backend is written in Rust. Validation failures use the exact JSON shape Laravel returns, so existing form libraries keep working.

Nested structs are flattened with dots and lists with indexes (items.0.name). Rules without a custom message fall back to a generic sentence that names the field and rule.

The Validate derive generates code that refers to ::validator, so your crate needs validator (with the derive feature) and serde as direct dependencies.

The Basics

Route Model Binding

Nearly every route with an ID starts by loading a record and returning 404 when it's missing. Route model binding does that for you: ask for Bind<Post> and you receive the post, or the client receives a 404.

Binding models

Models built with #[derive(Model)] bind automatically from any state that holds a DatabasePool. There is nothing to register.

Oxide reads the parameter named after the model ({post} for Post), or the only parameter if the route has just one. A value that doesn't parse as the key type, such as /posts/abc, is a 404 too.

Custom binding

Sometimes a record lives somewhere other than your database, such as a cache or an external API. Implement RouteBindable yourself and Bind works exactly the same way.

Return Ok(None) for a missing record and Oxide answers with a 404; return an error to fail with that error's status.

Rename the parameter a derived model binds to with #[model(route_param = "episode")].

The Basics

Error Handling

Consistent errors make an API pleasant to consume and safe to expose. Every Oxide error renders as Laravel-shaped JSON with the right status code, and database failures are reduced to an opaque message before they reach the client.

The error type

A single error type keeps handler signatures simple and lets ? do the work. OxideHttpError implements IntoResponse, so you can return it straight from a handler.

VariantStatusBody
BadRequest(String)400{"message": "..."}
Forbidden(String)403The message, or "This action is unauthorized." when empty
NotFound(String)404{"message": "..."}
Validation(ValidationErrors)422The Laravel validation shape
Internal(String)500{"message": "..."}, sent verbatim

The message you give Internal, BadRequest, Forbidden or NotFound is sent to the client as-is. Log diagnostics such as SQL, file paths or stack traces, and return a generic message like "Server Error" instead.

Database errors

A failed query should never leak table names or SQL to the outside world. OrmError converts into OxideHttpError: a missing row becomes a 404, and any other database error becomes an opaque {"message": "Server Error"} 500.

Keeping the cause: OxideHttpError::server

OxideHttpError::server(error) answers {"message": "Server Error"} but keeps the real error attached for reporting. OrmError uses it, so a database failure is logged with its SQL error and still tells the client nothing.

Your own errors: DomainError

The exception handler

An Application sends every error response through an ExceptionHandler, the Oxide version of Laravel's exception handler. The default handler reports server errors (one error log line with the cause chain, the request, and the request id from the log context) and never 4xx errors, and it renders JSON for API clients and a small HTML page for browsers, chosen from the Accept header (by q value, then order) and marked Vary: Accept. A 422 page lists the failed fields. Both hooks are replaceable:

The handler sees errors that are OxideHttpErrors. Axum's own extractor rejections (for example a malformed body for a plain Json<T>) are not, so they bypass it; use Validated<T>, which reports problems through the Laravel error contract.

.debug(true) adds the exception chain to JSON and HTML responses, but only when the environment is local. In staging or production, or when no configuration was supplied, it does nothing, so a stray debug flag can't leak internals.

The Basics

Support Helpers

The small helpers that make Laravel code read well: collections, strings, arrays, numbers, relative dates, pipelines and retries. Rust's iterators already cover much of Collection, so Oxide adds only what is missing.

Collections

There is no Collection type: CollectionExt adds the missing methods to every iterator, so they work on a Vec, a slice's .iter(), a map or a lazy stream. chunk and unique_by return lazy iterators, so they never load a whole result set; that is Oxide's LazyCollection.

The Basics

Logging

Oxide logs through tracing, with Laravel's idea of channels on top: you configure where logs go in config/logging.toml, and every line carries the request's id and any context you add.

Writing logs

The tracing macros (re-exported as oxide::tracing) give you structured fields. Log::info, Log::error and the rest are shortcuts for plain messages, and Log::channel("audit") addresses one channel.

Channels

stackFans out to the channels listed in channels.

The default channel, and the channels in its stack, receive every event. Other channels, like audit above, receive only events addressed to them with Log::channel("audit") or tracing::info!(channel = "audit", ..). Each channel has its own level (error, warn, info, debug, trace or off). Addressing a stack by name (Log::channel("stack")) reaches every channel in it. File channels write on a background thread and never drop lines: if the writer ever falls behind, logging waits for it. Text lines escape line breaks in messages, so logged input can't forge entries, and records from dependencies that use the log crate flow into the same channels.

Install the logger once, and keep the guard it returns alive; dropping it flushes the files:

Mistakes in the file (an unknown channel, a stack that loops back on itself, a bad level, a missing path) are errors at start-up.

Context

A Context is a set of key/values that every log line in the current request carries. Application starts one for each request and fills in request_id, method and path:

The response carries the id in an X-Request-Id header. A client's own X-Request-Id is reused if it is short and made of letters, digits and -_.:, so you can follow one request across services. A context belongs to one task: a task you tokio::spawn starts empty, so pass it a snapshot if it should log with the request's context.

Database

Database: Getting Started

Almost every application stores data, and connecting to a database should be the least interesting part of your day. DatabasePool wraps a sqlx pool for SQLite or PostgreSQL and is a service like any other, so handlers can ask for it directly.

Connecting

You create the pool once at startup and put it in your container. Every handler that takes db: DatabasePool receives a cheap clone of it.

The URL's scheme picks the driver, so switching databases is a configuration change, not a code change.

DriverExample DATABASE_URL
SQLitesqlite://database/database.sqlite?mode=rwc
PostgreSQLpostgres://oxide:secret@localhost:5432/podcasts

PostgreSQL

SQLite is built in, so a fresh project needs nothing else. PostgreSQL support is a cargo feature: you only compile its driver when you use it.

Hosted databases usually require TLS (sslmode=require or verify-full in the URL). Enable postgres-tls instead, which adds rustls with your system's root certificates. Without it, Oxide connects in plaintext only, so keep plain postgres for local servers.

Your models and queries don't change. The query builder writes $1, $2, … placeholders for PostgreSQL and ? for SQLite, and every value is still bound, never formatted into the SQL.

Rust's i64 is a PostgreSQL BIGINT. Declare integer columns as BIGINT or BIGSERIAL; an INTEGER column fails to decode into an i64 field at runtime. Also note that LIKE, behind where_title_contains and friends, is case-sensitive on PostgreSQL but not on SQLite.

Migrations

Your schema should live in version control and be applied the same way on every machine. Oxide uses sqlx's migrator: numbered SQL files in database/migrations, embedded into your binary at compile time and recorded in a _sqlx_migrations table so each runs exactly once.

Running migrate at startup is safe: applied migrations are skipped. Add a build.rs with println!("cargo:rerun-if-changed=database/migrations"); so new files trigger a rebuild.

Fresh databases for tests

Tests are fastest and most reliable when each one starts from a clean database. connect_fresh is Oxide's take on Laravel's RefreshDatabase: give it your usual URL and it hands back an empty database that belongs to that one test.

For SQLite you get a private in-memory database with foreign keys enabled. For a postgres:// URL, Oxide creates a uniquely named oxide_test_* schema and pins the pool to it, so your tests can run in parallel against one server.

Point PostgreSQL tests at a throwaway database. The test schemas are left behind so you can inspect them after a failure.

When you just need a table or two, connect_in_memory and execute_schema still work.

Raw sqlx access

An ORM should never trap you. as_sqlite() and as_postgres() return the underlying sqlx pool for anything the query builder doesn't cover yet, and driver() tells you which one you have.

Always pass values with .bind(..). Never format! user input into SQL, even when it looks harmless.

Eloquent Models

A model is the vocabulary your application uses to talk about its data. #[derive(Model)] turns an ordinary struct into an Eloquent-style model with typed queries, active-record methods and route binding, all generated at compile time.

Defining models

Start from a struct that sqlx can read from a row, then add the derive. Oxide works out the table name and primary key from conventions you already know.

Conventions

Following conventions means less configuration, but you can override each one.

ConventionDefaultOverride
Table namesnake_case plural: BlogPost → blog_posts#[model(table = "...")]
Primary keyThe field named id#[model(primary_key)] on a field
Route parametersnake_case type name: {post}#[model(route_param = "...")]
Column namesThe field names#[sqlx(rename = "...")], #[sqlx(rename_all = "...")]

What the derive generates

Knowing what exists saves you a trip to the source. For a Post model you get:

  • Static methods: Post::query(), find, find_or_fail, all, insert and create.
  • Instance methods: post.save(&db) and post.delete(&db).
  • A query builder, PostQueryBuilder, with typed methods for every field. See the Query Builder.
  • A NewPost struct with every field except an integer primary key, for inserts.
  • RouteBindable for every state that provides a DatabasePool, so Bind<Post> just works.

Mapping column names

Your database schema doesn't always match Rust's naming conventions. The derive honours sqlx's own rename attributes, so the columns it queries are always the ones FromRow reads.

Field options the model cannot mirror, such as #[sqlx(skip)], flatten, json and try_from, are compile errors rather than silently broken queries. So are two fields whose generated methods would collide, like score and score_gt.

Database

Query Builder

Queries are where typos hurt most, because they only fail when the code runs. Oxide generates a method for every column and comparison, so a misspelled column or a string compared to a number is caught by the compiler.

Retrieving models

Start a query with Model::query(), chain constraints, then finish with a terminal method. Nothing touches the database until you call that last method.

Where clauses

Each field gets the comparisons that make sense for its type. Strings get pattern matching, numbers get ranges, and Option fields get null checks.

Field typeMethods
Every fieldwhere_<field>(value), where_<field>_not(value), where_<field>_in(values)
String_contains, _starts_with, _ends_with
Integers and floats_gt, _gte, _lt, _lte
Option<T>_null(), _not_null()

Search terms are safe to pass straight from users: _contains, _starts_with and _ends_with escape % and _, so "50% off_" matches literally.

Ordering and pagination

Lists need a stable order and a way to page through them. Every field has order_by_<field>_asc and _desc, and any query takes limit and offset.

Terminal methods

The last call in a chain decides what you get back. Pick the one that matches what your handler needs.

MethodReturns
get(&db)Vec<Post>
first(&db)Option<Post>
first_or_fail(&db)Post, or OrmError::NotFound (a 404 over HTTP)
count(&db)The number of matching rows
delete(&db)The number of rows deleted
to_sql()The SQL and bound values, for debugging

Reach for find_or_fail and first_or_fail in handlers. They turn a missing row into the same 404 that route model binding returns, with no match needed.

Database

Inserting & Updating Models

Changing data should read like a sentence about your domain. Oxide gives you Eloquent's active-record verbs, typed so you can't forget a required column.

Inserting

Inserts take the generated New<Model> struct, so the compiler lists every column you must provide. The stored row comes back, database defaults and generated ID included.

create takes the struct by value; insert(&db, &new_post) borrows it. Both use INSERT ... RETURNING *.

Updating

Load a model, change its fields, save it. save writes every column back by primary key and returns NotFound if the row has disappeared in the meantime.

Deleting

You can delete a model you already hold, or every row a query matches. The query form tells you how many rows it removed.

Database

Relationships

Data is connected, and your code should follow those connections without hand-written joins. Relationship helpers return the related model's query builder, so you keep every typed method.

Defining relationships

A relationship is a foreign key and a direction. Call has_many, has_one or belongs_to with the foreign-key column, then keep chaining.

These are methods of the Model trait, which oxide::prelude::* brings into scope. has_one returns the same builder as has_many; finish it with first.

Testing

HTTP Tests

The best test of an API is a request, and writing one should take seconds. TestClient sends requests straight into your router, with no server or port, and gives you chainable assertions that print the response body when they fail.

Making requests

Wrap your router, build a request, send it and assert. Each request runs through your full middleware stack and extractors, exactly as it would in production.

Requests start from get, post, put, patch or delete, and take .header(..), .json(&payload), .form(&payload) or a raw .body(..).

Available assertions

Assertions return the response so you can chain as many as you need. When one fails, the message includes the status and body so you rarely need a debugger.

AssertionChecks
assert_ok, assert_created, assert_no_content200, 201, 204
assert_bad_request, assert_forbidden, assert_not_found, assert_unprocessable400, 403, 404, 422
assert_status(StatusCode::..)Any status
assert_header(name, value)A response header
assert_json_path(path, value)A JSON value by dot path (data.0.title) or JSON pointer (/data/0/title)
assert_validation_error_for(field)A 422 with an error for that field

You can also read the response directly with status(), headers(), text(), json() or json_as::<T>().

Testing with a database

A test that hits a real database proves the whole path works, not just the handler. Give each test its own in-memory database and check the stored rows after each request.

Test the failure paths as carefully as the happy path. A 404, a 403 and a 422 per resource catch more regressions than a dozen happy-path tests.

The AI Agent Skill

AI coding agents write code the way their instructions tell them to. Oxide ships its house style as an agent skill, so Claude Code and Cursor write the same idiomatic, zero-cost Rust you would.

Where it lives

One source of truth avoids two sets of rules drifting apart. The skill is written once and mirrored into Cursor's format by a script.

AgentFile
Claude Code.claude/skills/oxide-eloquent-rust/SKILL.md
Cursor.cursor/rules/oxide-eloquent-rust.mdc (generated)

CI fails if the Cursor rule is out of date, so the two can never diverge on main.

What it teaches

Good conventions are short enough to remember and specific enough to check in review. The skill boils Oxide's style down to a handful of rules.

  • A three-layer trace for every feature: domain intent, then the Laravel way to express it, then the zero-cost Rust mechanics that deliver it.
  • Failure first, happy path last, with let ... else and ? instead of nested if blocks.
  • Five-action resource controllers; other verbs become single-action controllers or Action structs.
  • Hard rules: no unwrap or expect in library or handler code, no lock guard across .await, and only bound SQL parameters.

The skill is also a good checklist for human reviewers. Its last section is a review checklist you can paste into a pull request.
